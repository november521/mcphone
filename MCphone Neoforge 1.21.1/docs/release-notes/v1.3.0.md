# MCphone v1.3.0

这一版几乎不改变你在游戏里看到的东西，改的是这个模组的底子 —— 让别人也能往这部手机里装自己写的 App。

**运行环境：** Minecraft 1.21.1 · NeoForge 21.1.200 或更高 · 客户端与服务端都需安装
**可选：** Curios —— 装了多一个手机槽
**可选：** Waystones（传送石碑）—— 装了多一个「传送石」App
**可选：** MCEF —— 装了多一个「浏览器」App

**从 1.2.5 升级：** 直接替换 jar。存档、购买记录、App 安装状态都不受影响。

---

## 🙋 给玩家的：几乎没有变化

这一版对着屏幕能看出来的只有两处：

- 应用商店里的「联动App」入口从**第一格挪到了最后一格**。商店首页第一眼该是能下载的东西，联动那一页说的是「还能有什么」——它不是一个 App，是一份说明，本来就该排在正事后面。
- 装了写坏的附属模组时，手机不会再变成空的。**详见下一节**。

其余全是底下的事。功能一个没删，操作一处没改。

## 🛡️ 一个附属写坏了，不再连累所有人

**这是这一版最该被记住的修复。**

App 是靠 Java SPI 发现的，而原来的扫描写法有个坑：某个附属的 App 类构造失败（类名写错、构造函数抛异常、没有无参构造），整个扫描当场中断——**内建的十个 App 一个都登记不上**，手机里空空如也。而且那个"已加载"的标志早就置真了，这一局都不会重试。

玩家看到的是「装了某个模组之后手机里什么都没有了」，报错还指向别人的模组。

现在坏的那个被单独跳过并记一条日志，写明是哪个类干的，其余照常加载。

开放的前提是**一个人写坏了不能连累所有人**——不做到这条，「谁都可以写 App」就只是句口号。

## 🎨 给资源包作者：贴图路径变了，老的仍然认

原来十七张贴图平铺在 `textures/gui/` 下，App 图标、手机外壳、聊天气泡、商店按钮、浏览器面板全挤在一起，靠文件名前缀区分。现在按功能分了目录：

| 目录 | 装什么 |
|---|---|
| `textures/app/` | App 图标，文件名就是 App 短名（`camera.png`、`chat.png`…），20×20 |
| `textures/phone/` | 手机本体：外壳、状态栏、导航栏、导航键、通知、角标 |
| `textures/chat/` | 聊天气泡与输入栏 |
| `textures/store/` | 商店按钮、联动入口 |
| `textures/browser/` | 浏览器面板与工具条 |

完整对照表见 README 的「换肤」一节。

**你现有的资源包不用改。** 这些路径在 README 里作为换肤契约公开过两个版本，说改就改等于把你做好的东西单方面作废。新路径找不到时会自动回退到老路径，并在日志里提一句。新做的资源包请按新表。

`textures/item/` 与 `textures/slot/` 没动 —— 前者是原版模型约定，后者是 Curios 约定，都不由我们说了算。

## 🧩 给附属模组作者：这一版真正的主角

### 你的 App 现在可以画在手机屏幕里

在这之前，附属 App 被点开时只有一条路：`Minecraft.setScreen(new MyScreen())`——整个跳出手机。状态栏没了、导航栏没了、壁纸没了、返回键自己实现、关掉之后回哪儿自己记。

而内建的聊天、记事本、相册全是手机屏幕里的一页，共用这一切。同一套 SPI 注册出来的东西，内建的能画在手机里、附属的只能跳出去——**那不是开放，是内建 App 有后门**。

现在覆盖一个方法就行：

```java
public final class CalculatorApp implements IPhoneApp {
    @Override
    public IPhonePage openPage() {
        return new CalculatorPage();
    }
}

public final class CalculatorPage implements IPhonePage {
    @Override
    public void render(PhoneCanvas c) {
        c.graphics().drawString(c.font(), "1 + 1 = 2",
                c.x() + 4, c.y() + 4, c.style().bodyColor(), false);
    }
}
```

状态栏、导航栏、壁纸、手机外壳由 MCphone 画。`PhoneCanvas` 给的坐标是**内容区**，那两条已经替你扣掉——你不需要知道它们多高，我们改了你也不受影响。

`IPhonePage` 里只有 `render` 是必须实现的，点击、滚轮、按键、返回、生命周期全是可选。**返回 null 走老路**，已经写好的 App 一行都不用改。

界面在 120×200 里真的放不下时（比如网页），继续用 `onPress()` 跳出去——内建的浏览器就是这么做的。

### 你的页面长得像手机里的东西

`PhoneStyle` 开放了手机当前的配色：标题色、正文色、次要色、强调色、按钮的三种状态……照着画就融进去了。

它是**接口**不是常量，这一点是刻意的：常量会被编译器内联进你的 class 文件，我们哪天换了配色，你那边的字面量还是编译当天的值，而且没有任何迹象表明哪里不对。走接口每次都是真实调用。

### 打字不会再把手机关掉

原版背包键默认是 E。玩家在你的输入框里打字，一按到 e 就命中背包键，手机当场关掉、内容全丢——打拼音一定会按到 e，中文用户躲都躲不开。

`IPhonePage.capturesKeyboard()` 返回 true，按键就先给你的页面。MCphone 自己的设备命名、聊天输入、笔记编辑三处都是这么处理的，现在你也有同样的手段。

### 你的页面抛异常，只关掉你这一页

每个回调都被兜住了（兜的是 `Throwable` 不是 `Exception`——引用了没装的模组里的类抛的是 `NoClassDefFoundError`，属于 `Error`）。你这一页抛异常只会让它被关掉并记一条日志，不会拖垮手机界面，更不会崩游戏。

抛异常的页面会被**当场关掉**而不是留着每帧再抛——那样日志一秒能刷几千行，第一条真正的错误反而被冲掉。

### 写下来的兼容承诺

新增 `MCphoneApi`，两样东西：

- **`VERSION`** —— API 代号，每次加能力 +1、只增不减。想同时支持新旧两版 MCphone 时拿它判断。
- **五条兼容策略**，写在类注释里：不给已发布的接口加抽象方法；不改已发布记录的构造函数；不改已发布的方法签名；包名也是 API；这些规矩只管 `api` 包。

写在代码里而不是 README 里，是因为**改 API 的人一定会打开这个类，不一定会去翻文档**。

### `AppInfo` 改用 builder

它原来是个七字段的 record。record 的规范构造函数是公开 API 的一部分——哪天要加第八个字段，所有写了 `new AppInfo(...)` 的附属当场编译不过。

这与「加功能不打断附属」的承诺在结构上冲突。不是我们会不会小心，是那种写法根本不给你小心的余地。

```java
AppInfo info = AppInfo.builder(id, displayName, sourceId)
        .icon(iconTexture)
        .version("1.0.0")
        .author("someone")
        .description("这个 App 是干什么的")
        .build();
```

趁现在改是因为第三方附属数量约等于零。晚一步这就是永久债务。

### API 包重新分组

```
api/client/app/     写一个 App（IPhoneApp、RequiredMod）
api/client/store/   接入商店（IAppSource、AppInfo）
api/client/ui/      画在手机里的页面（IPhonePage、PhoneCanvas、PhoneStyle）
api/cost/           代价与定价，两端安全
```

`api.client.*` 是客户端专用，其余两端安全——这条老规矩没变，只是加了一层主题分组。

**注意 SPI 服务文件名跟着变了**：`META-INF/services/com.november.mcphone.api.client.app.IPhoneApp`（原来是 `...api.client.IPhoneApp`）。

## 🏗️ 底层：128 个文件按功能重排

原来是按「技术类型」分包的：所有界面在 `gui/`、所有网络包在 `network/`、所有数据在各自的包。改一处聊天要在四个包之间跳，而 `gui/` 一个包里塞了 25 个文件 7833 行。

现在按功能分：

```
core/          手机本体：物品、注册、外壳、主题、贴图、导航、App 目录
feature/       十个功能各一个包，界面 + 数据 + 网络包全在一起
compat/ util/  联动兼容层与工具
```

每个 feature 包内三层：`feature/x/` 服务端与两端共用、`feature/x/client/` 客户端专用、`feature/x/net/` 网络包。

**这对你有一个直接影响**：`api` 之外的一切都是内部实现，随时可能改，别引用。要用什么却发现只有内部有，提出来，我们把它挪进 API——这比你引用内部类、然后在某次更新里无声地坏掉要好。

## 🚨 两道构建期防线

重排包结构顺手把两条只能靠"记得"的规矩变成了构建失败：

**`verifyDistIsolation`** —— 路径里没有 `/client/` 的类，只要字节码常量池里出现客户端类型就直接构建失败。专用服务器上没有客户端类，一个类只要**常量池里写着**客户端类型，哪怕那段代码永远执行不到，被加载时就会当场崩服。

搜字节码而不是读源码是刻意的：未使用的 `import` 编译后根本不进常量池，而真正会让服务端崩的恰恰是常量池里那一条。

这个任务加进来几分钟后就拦下了第一次真实事故——拦的是作者自己：重组 API 时把 `IPhoneApp` 挪出了 `client` 路径，而它的签名里有 `GuiGraphics`。

**`verifyServiceFiles`** —— `META-INF/services` 里写的每个类，编译产物里必须真的存在。

这个失败模式极其阴险：那些文件是纯文本，编译器一个字都不看。类改名或搬包后忘了同步，**构建成功、jar 能装、启动不报错**，只是运行时一个实现都找不到，手机里空空如也。这一版重排包结构时差一点就这么发出去了。
