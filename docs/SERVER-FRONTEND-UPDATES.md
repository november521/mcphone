# 服务器前端更新与大包传输

这些代码已接入，最终真服验收尚待用户执行。自动化通过不能代替三个平台实际进服与重启测试。

## 内源更新

服主在世界 `serverconfig/mcphone-script-runtime.json` 的对应 `app_policy` 行中设置：

```json
{"id":"example:demo","frontend_update":"optional"}
```

`optional` 为默认值。玩家打开商店或设置详情时检查内源版本，在设置详情正文中点击“检查并更新服务器前端”执行更新。`forced` 在打开旧 App 时进入原生同步页，旧脚本不会接收点击；已打开的旧页面也会切到同步页。`off` 关闭更新提示，保留主动检查入口。

更新只取本服已批准、当前玩家可见的前端封套。服务器后端源码不下发；客户端重建原包摘要并验证原作者签名。元信息与 App id、完整作者公钥、原包摘要、整数 `versionCode`、前端摘要逐项绑定。简短指纹和展示版本用于界面显示。

同作者且版本提高、声明能力已被此服批准的前端可更新。作者换钥、版本回退、同版本不同签名内容、未批准的能力增量均停止自动替换。已安装 App 的设置详情提供「手动换作者或降级」原生页，核对完整公钥、指纹、明确的降级提示及默认未勾的确认。它不会绕过服主吊销、最低版本或签名冲突。

本地导入、服务器前端和外部 feed 共用 `config/mcphone/package-versions.json`。合法候选只记录证据，不抬高已用版本下限；已验签/编译候选先原子保存缓存，随后保存版本保护并切换注册。缓存写失败不抬高下限；签名冲突和见证历史读写失败仍停止使用，不能把坏历史当空历史。人工降级只记录精确摘要的例外，最高版本记录保持不变；普通自动路径不因此获准回退。

服主在 app_policy 明确写 `follow_author_updates:true` 或在原生管理为该 App 开启跟随，且启用 server_fetch 并允许 feed/下载域名后，宿主才检查外部作者 feed。两个有界 worker 做 HTTPS、ZIP 外签名、包内完整作者链和能力增量检查，落地前重查当前授权与政策。同权限新版可自动升级；新增 granted/restricted 进入带原因的待审队列，旧已批准版本继续运行。默认六小时缓存，关闭设置立即停止；升级保留原有玩家许可，不自动开放所有人。

## 文件通道

原生商店新增 `store_file` / `store_file_reply`，每片最大 16 KiB，按确认串行发送，片间隔 250 ms。1 MiB 包为 64 片，传输硬时限仍为 60 秒。普通脚本 RPC 的参数和结果保持 4 KiB。

服务端按登录 UUID、连接 epoch、随机会话号和片序号绑定上传；完整接收后验证原始字节 SHA-256，再解包、验签并进入审核队列。重复的前一片只有内容完全相同才确认。上传会话仍预留全量内存，最多 32 会话，按服主 `upload.server` 配额约束。

文件上传一分钟字节预算为 `max(512 KiB, 2 × package.compressed)`，仅服主提高包上限时扩展；普通旧通道仍保留原 512 KiB 预算。断线不能清字节预算。下载每玩家每分钟最多两份硬上限前端封套，全服合计 64 MiB；每片重新检查当前信任、吊销和可见性。

服务端通过宿主网络策略声明文件通道版本及压缩/解压包上限。客户端只在声明兼容时使用新包，老服务器走原 2 KiB 路径；不能在 60 秒内完成的旧通道大文件会提示升级服务器。

## 本阶段人工测试任务

1. 三个平台各用正常签名包进行一次上传、审核、安装，确认客户端没有 `server.js` 源码。
2. 提高压缩上限到 1 MiB、解压上限到 4 MiB，上传大于 256 KiB 的合法包；完整下载后能打开。默认限额仍拒绝该上传。
3. 上传中断线、换世界、关闭连接；旧会话不能继续提交，新会话不串入旧片。乱序片、改动的重传片和超过 16 KiB 的片被拒绝。
4. 安装版本 1 后批准版本 2。optional 先显示更新入口，主动更新后重开运行版本 2；forced 在打开旧页和页面已打开时均要求同步；off 不弹新版本提示。
5. 用另一把作者密钥签同 id 包，确认不会自动替换。伪造服务器元信息里的完整公钥、版本或任一摘要，确认拒绝。
6. 同一作者同一 `versionCode` 签两份不同内容，即使是已归档旧版本也应停止该作者/App 的所有版本；重启后保持停止。另一把已单独确认的完整公钥不受该作者的冲突下限影响。
7. 用服主策略撤销旧客户端持有的版本或摘要，打开页面核对实际版本；页面不再响应脚本输入。权限核对期间收到的钱包结果不得被当成失败而自动重试。
8. 更新期间填满磁盘或损坏版本历史，确认显示失败原因且不运行半更新包；修复并重启后再检查。测试前备份测试世界与客户端配置。
