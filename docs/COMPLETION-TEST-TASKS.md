# MCPhone 自行验收任务

这份清单由你在自己的客户端和服务器执行。三平台自动构建的结果单独记录；以下游戏任务目前全部为「未测」。优先完成 T01–T19、T20–T25，再测试外部依赖及故障窗口。

## 安装与准备

1. 选择与 Minecraft 和加载器完全匹配的 JAR；客户端与服务端使用同一份校验值。Forge 1.20.1 使用 Java 17；NeoForge/Fabric 1.21.1 使用 Java 21。这是尚未发布的测试构建，沿用仓库版本号，不代表 GitHub 正式发布。
2. 使用备份后的测试世界。先用 MCPhone 和必要依赖启动，再做 KubeJS/经济/资源模组共存测试。旧配置、旧世界迁移与全新世界分别记录结果。
3. 在世界 `serverconfig/mcphone-script-runtime.json` 中，把测试管理员 UUID 加入 `admin.deployment_approvers`、`admin.store_reviewers`、`admin.gift_editors`；服务器给同一玩家 OP 3 或以上。名单只改文件。原生管理每次仍由服务器核对身份与 OP。
4. 首次启动的 `server_scripts` 默认为 false。进入原生「服务器管理」预览并开启；已有配置也必须明确填写 true。切换预设后会重新关闭，需要单独开启。
5. 将对应版本的数据包目录放进测试世界的 datapacks，执行 `/reload`。其 `myserver:daily_gift` 给两颗钻石，`#mcphone:giftable` 包含钻石。1.20.1 使用 `loot_tables/predicates/tags/items`，1.21.1 使用 `loot_table/predicate/tags/item`，不混用。
6. 需要钱包时，把附带 `economy-server-a.json` 作为世界 `serverconfig/mcphone-economy.json`，重启核对默认 `win:coin`。B 配置用于第二台测试服，外部 scoreboard 等提供者不可用时应明确显示不可用。
7. 最初只放 `server-v1.zip` 到世界 `mcphone/store/incoming/`，在控制台执行 `/mcphone script scan`，通过原生作品/审核/部署页核对签名、审核上架、批准动作和能力，再授权自己。客户端从内源商店安装。纯前端 `frontend-v1.zip` 放客户端游戏目录 `mcphone/apps/` 后在原生商店安装。
8. 查看 `fixture-index.json` 的完整公钥、指纹、版本和摘要。测试密钥没有交付私钥，不能用于正式作品。不要一开始就把多个同 ID 版本一起放入本地目录；按下面用例逐个切换候选文件。

## 成功外网与作者跟随更新

验收包的固定样例声明 `example.com`，用于默认关闭、许可及非 PNG 拒绝用例。没有搭建外部测试站点，不能把这些样例写成联网验收已通过。

如果你有自己控制的公共 HTTPS 测试域名，在仓库运行 `tools/Generate-CompletionFixtures.ps1 -TestDomain 你的域名 -JdkHome 你的Java21目录`。它只生成新的测试作者及签名样例，不联网、不修改正式游戏目录。生成后使用新目录中的整套版本与 fixture-index，不混合旧验收包里的作者版本。

将生成目录的 ZIP、XML 和 icon.png 部署到该域名 `/mcphone/` 下，禁止重定向。开启服务器允许域名及 server_fetch；在原生管理只对 `completion:server` 打开「跟随作者更新」。最初部署 v1，server-appcast.xml 指向 v2；同权限新版可升级且保留原许可。随后用 server-appcast-permissions.xml 的内容替换远端 server-appcast.xml，v3 新增 effect.give 必须进入待审队列，已批准 v2 继续运行。默认六小时检查缓存，测试重新检查可使用原生配置重载，不能修改见证下限。

玩家前端更新则单独允许其作者 feed，frontend-appcast.xml 指向 v2。测试断网、坏外签名、坏包内签名、错误完整公钥和新增能力；旧包不能在验证之前被替换。私人图片 URL 填 `https://你的域名/mcphone/icon.png`。

## 故障窗口及验收记录

按 `NATIVE-ADMIN-TESTS.md` 的 A1–A11、R1–R7 补测权限、事务中断、外部钱包异常和双账核对。R1 需要具有「入账后抛异常」行为的测试经济提供者；没有该依赖时标「未测：缺少故障提供者」，不能用内置断言结果代填游戏验收。

每个平台单独记录：用例编号、JAR SHA-256、MC/加载器/Java/共存模组版本、前置数据、步骤、预期、实际、通过/失败/未测、日志与截图位置。金额和物品用真实账本/背包核对，toast 不足以证明落地成功。失败时保留原日志、UTC 审计及保护存档，不清空 UNKNOWN 或见证记录来继续测试。
